PROTOCOL STATUS
What this build does
  • Creates random, expiring, single-use identity challenges.
  • Verifies Nostr event signatures and BCH compact message signatures locally when the pinned cryptographic dependencies are installed.
  • Requires both proofs before issuing an identity binding.
  • Stores challenge and binding records in SQLite by default, with atomic challenge consumption and duplicate-binding protection.
  • Exports portable proof bundles for independent verification without the local database.
  • Supports Nostr relay publishing and discovery when relays are configured and reachable.
This is a local single-process MVP candidate, not a production multi-user deployment. WizardConnect pairing is a separate wallet-session feature and does not itself prove BCH message signing. Real wallet pairing, NIP-07 extension signing, and live relay operation must be tested in their respective environments. Network-aware transaction tools require BCH Node RPC configuration for the selected network.


08 / BCH TRANSACTION INSPECTOR · NETWORK-AWARE
Inspect an unsigned or signed transaction
Parse a raw legacy BCH transaction locally through the KEYSTONE server. Review inputs, outputs, scripts, transaction ID and fee calculations before considering a wallet signature. This does not prove UTXOs exist or validate consensus/script rules.


What the result means
A successful result means the two signatures were verified for the same challenge. It demonstrates control of both identities at the time of signing; it does not establish a person's legal name or real-world identity.
